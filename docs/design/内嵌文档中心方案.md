# 内嵌文档中心方案（VitePress 接入）

> 状态：设计稿 v1.0，2026-05-10
> 后端契约：已落地 `GET /api/console/auth/check`（轻量鉴权探针，详见 `../file-batch-system/docs/api/console-api-protocol.md`）
> 前端落地：未开始

## 背景与目标

后端仓 `../file-batch-system/docs/` 沉淀了 169 篇 markdown（ADR、architecture、runbook、design、analysis、api、coding-conventions），三类受众都要看：

| 受众 | 关心的文档 | 典型场景 |
|------|------------|----------|
| 内部开发 / 架构师 | ADR-001~027、design/、analysis/、coding-conventions | 新功能立项前查 ADR、改代码前对照规范 |
| 运维 / SRE | runbook/、feature-switches、releasing、cleanup | 处理告警、做发布、查开关、走 cleanup 流程 |
| 业务用户 / 操作员 | 操作手册、字段说明、错误码对照 | 控制台日常使用，遇到不懂的字段或错误码现场查 |

**目标**：把这 169 篇文档以"嵌入控制台"的形态展示给用户，分类清晰、能搜、加载快、跟随 git，按角色过滤可见范围。

**非目标**：
- 不做在线编辑 / CMS（运营改文档统一走 git PR，与代码同评审）
- 不做多语言切换（文档现状中英混排，跟随后端文档语言策略）
- 不引入外部 SaaS（Algolia DocSearch / GitBook / Confluence）

## 方案选型

| 方案 | 工作量 | 维护成本 | 嵌入度 | 决策 |
|------|--------|----------|--------|------|
| A. **VitePress + nginx 子路径反代** | 1 小时出第一版，1 天调样式 | 几乎为零（Vue 团队亲生，跟随 Vite 升级） | 同域子路径，从控制台菜单点进去 | ✅ **采用** |
| B. **VitePress + iframe 嵌控制台 layout** | 同 A + iframe 包装 | 同 A + iframe 路由同步逻辑 | 视觉上"在控制台内"，但路由割裂、双滚动条 | ❌ |
| C. **独立子域名（docs.xxx）** | 同 A | 同 A | 完全独立站点，与控制台割裂 | ❌（运营约束：必须从控制台进入） |
| D. **batch-console SPA 内自拼**（markdown-it + el-menu） | 2-3 天 | 持续维护渲染管线、搜索、TOC、mermaid、相对链接重写 | 完全融入 SPA shell（共享主题、登录态、路由） | ❌（重造 VitePress） |

### 为什么是 A 而非 D

D 方案唯一胜过 A 的地方：**deep theme integration / contextual help / 共享登录态**。前两者属于"如果之后真有需求再说"的范畴；最后一个用 nginx `auth_request` 打到后端 `/api/console/auth/check` 即可解决，不必自拼。

D 方案的代价：169 篇 markdown 的渲染、TOC、锚点、mermaid、shiki、搜索、相对链接重写、frontmatter 解析等全要自己实现 + 持续维护，本质是重造一个差点意思的 VitePress。

## 整体架构

```
                ┌─────────────────────────────────────────┐
                │  浏览器                                   │
                │                                          │
                │   /                  /docs/architecture/ │
                │   ↓                  ↓                   │
                │  Vue SPA (控制台)    VitePress 静态产物   │
                └──────┬──────────────────────┬────────────┘
                       │                      │
                       │ JWT (cookie/header)  │ 同 JWT
                       ↓                      ↓
                ┌──────────────────────────────────────────┐
                │  nginx                                    │
                │                                           │
                │  location / { → batch-console SPA 静态 }  │
                │  location /api/ { → console-api:18080 }   │
                │  location /docs/ {                        │
                │    auth_request /__auth_check;            │
                │    alias /var/www/batch-docs/;            │
                │  }                                        │
                │  location = /__auth_check {               │
                │    internal;                              │
                │    proxy_pass http://console-api:18080    │
                │               /api/console/auth/check;    │
                │  }                                        │
                └──────────────┬────────────────────────────┘
                               │
                               ↓
                       ┌────────────────┐
                       │  console-api   │
                       │                │
                       │  GET /api/     │
                       │   console/auth │
                       │   /check → 204 │
                       └────────────────┘

  build 时：
    file-batch-system/docs/**/*.md
        ↓ vitepress build (base: '/docs/')
    /var/www/batch-docs/  (静态 HTML/JS/CSS)
```

| 层 | 形态 | 路径 / 端口 |
|----|------|-------------|
| Vue SPA | Vite build → 静态 | nginx `/` |
| VitePress 文档站 | VitePress build → 静态 | nginx `/docs/` |
| console-api | Spring Boot | `:18080`，nginx `/api/` 反代 |
| 鉴权 | nginx `auth_request` 子请求 → `/api/console/auth/check`（204/401） | 内部专用，不对外 |

## 关键设计点

### 1. 跨仓引用 docs/，跟随 git

文档源在 `../file-batch-system/docs/`，**不复制、不 submodule**，VitePress build 时直接 `srcDir` 指过去。

参考已有的 `gen:api` 模式（`package.json:11`）：
```
openapi-typescript ../file-batch-system/docs/api/console-api.openapi.yaml ...
```

VitePress config 同款写法：
```ts
// docs-site/.vitepress/config.ts
import { defineConfig } from 'vitepress'
export default defineConfig({
  srcDir: '../../file-batch-system/docs',
  base: '/docs/',
  outDir: '../dist-docs',
  // ...
})
```

本地开发约束：必须把 `batch-console` 与 `file-batch-system` 放在同一父目录下（已有约束，AGENTS.md 明确）。

### 2. nginx 鉴权：反代而非嵌入

**不做**：把 docs HTML 塞进 SPA 的 router-view 里。
**做**：nginx `auth_request` 拦 `/docs/*` → 调 `/api/console/auth/check` → 204 放行 / 401 跳登录页。

后端契约（已落地）：

```
GET /api/console/auth/check
  - 已登录: 204 No Content
  - 未登录: 401 + ResultCode.UNAUTHORIZED（走 SecurityConfig entryPoint）
  - 不查 DB、不组菜单（区别于 /api/console/auth/me）
```

未登录时 nginx 应返回 401，前端 SPA 通过现有 axios 拦截器处理跳转登录。两种实现方式：
- **简单**：直接让 nginx 返回 401，让浏览器 → 看到非 SPA 资源 → 用户被引导回 `/login`
- **更顺**：nginx 配 `error_page 401 = @redirect_to_login;` 跳到 SPA 登录页

### 3. 角色过滤（按需，P2 阶段实现）

文档对受众分级，避免业务用户看到 ADR / analysis 这类内部讨论。

**做法**：每篇 .md 顶部加 frontmatter：

```markdown
---
audience: [dev, sre]   # dev | sre | user 三选 N
---

# 文档标题
...
```

VitePress 自定义主题在 sidebar 渲染前调 `/api/console/auth/me` 拿 role，client-side 过滤掉当前用户不应看到的条目。**注意**：这是 menu 层过滤，文件本身仍是公开静态资源，知道 URL 仍可访问 — 真正的访问控制靠 nginx auth_request（即 P0 的方案 B）。

| audience | 默认对应控制台角色 | 文档样例 |
|----------|--------------------|----------|
| `dev` | `ROLE_ADMIN` | ADR、design、analysis、coding-conventions |
| `sre` | `ROLE_ADMIN` / `ROLE_OPERATOR` | runbook/、feature-switches、releasing |
| `user` | 所有登录用户 | 字段说明、操作手册、错误码对照 |

**不打 audience 的文档默认 `[dev]`** —— 现有 169 篇默认都按 dev 处理，新加文档显式声明 audience。

### 4. 渲染能力（VitePress 开箱即用）

| 能力 | VitePress 内置 | 备注 |
|------|----------------|------|
| 代码高亮 | shiki | 主题质量好，跟控制台暗色主题可对齐 |
| Mermaid | 需配 `markdown-it-mermaid` 插件 | 后端 ADR 大量使用 |
| TOC | 自动从 `##` 生成 | 右侧浮动 |
| 锚点 | 自动 + 滚动定位 | `#section-id` |
| 搜索 | local search（minisearch 内置） | 客户端全文，169 篇规模够用，不引 Algolia |
| 暗色主题 | 内置 | 跟随系统或手动切换 |
| Edit on Git | 配置 `editLink` | 跳转 GitLab/GitHub 编辑入口 |
| 相对链接 | 自动改写 .md → URL | 解决后端文档大量 `[xxx](architecture/yyy.md)` 链接 |

### 5. 部署产物

VitePress build 输出到 `dist-docs/`，nginx 静态指过去。生产部署：
- 容器化：单独一个 nginx sidecar 容器；或塞进 batch-console 同一个 nginx 镜像的 `/var/www/batch-docs/`
- 不容器化：CI build 完 rsync 到目标机器

## 后端契约（已落地）

| 端点 | 用途 | 状态 |
|------|------|------|
| `GET /api/console/auth/check` | nginx auth_request 探针，204/401 | ✅ 已落地（2026-05-10）|
| `GET /api/console/auth/me` | 文档站读 role 做 menu 过滤（P2 才用到） | ✅ 早已存在 |

## 落地阶段

| Phase | 内容 | 工作量 | 价值 |
|-------|------|--------|------|
| **P0 MVP** | VitePress 装起来 + `srcDir` 指向后端 docs + 默认主题 + nginx `/docs/` 反代（不做鉴权） | 半天 | 文档能在浏览器看到 |
| **P1 完整渲染** | mermaid 插件 + editLink + sidebar 配置（按目录分组） + 暗色主题与控制台对齐 | 1 天 | 文档有 docs 站该有的样子 |
| **P2 鉴权 + 受众过滤** | nginx auth_request 接入 + 控制台菜单加 "文档" 入口 + 给 169 篇 .md 补 frontmatter audience（增量逐步加，新增文档强制） + 自定义主题读 `/me` 做 menu 过滤 | 1.5 天 | 业务用户看不到 ADR、登录态打通 |
| **P3 上下文帮助**（可选） | 控制台功能页右侧抽屉（如 workflow 编辑页 → 嵌 ADR-009 DSL 语法）；用 markdown-it **单独**渲染特定文档片段（不替换 P0~P2 的整体架构） | 1 天 | 提升业务用户操作时的现场帮助 |

**第一周目标**：P0 + P1 上线，看效果决定 P2 是否继续。

## 风险与权衡

| 风险 | 缓解 |
|------|------|
| **跨仓 build 时 docs/ 不在场** | 本地：依赖 AGENTS.md 既有约束（同父目录）；CI：build 前 `git clone` 后端仓或拉取归档 |
| **后端文档大量相对链接** | VitePress 自动改写 `[xxx](foo.md)` → `/docs/foo`；不规范的 `../analysis/zzz` 跨目录链接需手动修；P0 阶段先观察 build warning |
| **mermaid bundle 大** | VitePress 按需 lazy；非 mermaid 页不加载 mermaid runtime |
| **169 篇文档全文索引体积** | minisearch 客户端索引压缩后估 ~1MB 量级，可接受；超过再考虑 Algolia |
| **角色过滤是 menu 层而非访问层** | 真正访问控制靠 nginx auth_request（P2 已含）；frontmatter audience 仅做 menu 整洁，不当访问控制用 |
| **后端文档体例不统一**（有的有 frontmatter 有的没有） | 默认值兜底（无 frontmatter 视为 `dev`）；新增文档强制 frontmatter，由 VitePress build hook 校验 |
| **后端 docs/ 改动后没人触发前端重 build** | CI 加跨仓触发（push docs/* → 触发 batch-console docs CI）；过渡期靠手工 `npm run docs:build` |

## 未来演进（不属本次方案）

- **Algolia DocSearch**：当客户端搜索体验扛不住或文档数破 500 篇时切换
- **多语言**：当真有海外用户/合规要求时启用 VitePress i18n
- **CMS 化**：当运营要绕开 git 改文档时再考虑（强烈不推荐 — 文档与代码版本错配是大坑）
- **Contextual Help SDK**：把 P3 抽成 batch-console 内的统一 SDK（`<DocsDrawer doc-key="adr-009-dsl">`），其他业务页可复用
