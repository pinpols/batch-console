# 服务端分页迁移指南（2026-04-19）

## 背景

当前前端 65 处调用 `fetchAllPageItems`，最多拉 `maxPages × 200 = 20000` 条记录做客户端过滤+分页。大租户场景下会明显卡顿，且完全吞掉了后端 `PageResponse` 的分页能力。

## 代表页（已完成）：`JobDefinitionList`

改动 3 个文件，总计 ~90 行：

- `src/api/job.ts`：新增 `listDefinitionsPaged` 返回 `{records, total, page, pageSize}`，用 `get(...)` 带 `pageNo/pageSize/jobCode/enabled`
- `src/composables/queries/useJobDefinitionsPaged.ts`：包 TanStack Query + `keepPreviousData`（翻页不闪）
- `src/views/job/JobDefinitionList.vue`：page / pageSize / jobCode / enabled 作为响应式 refs 传给 composable；后端不支持的次要 filter 走本页前端二次过滤

## 迁移模板

对任一 `ListXxx.vue` 页，按 6 步改：

### 1. 核对后端 OpenAPI 支持哪些 filter

`file-batch-system/docs/api/console-api.openapi.yaml` 里搜对应 `queryXxx` operation。看 `parameters` 里除了 `tenantId / pageNo / pageSize` 还暴露了哪些字段（例如 `jobCode`、`status`、`enabled`）。

### 2. API 层加 paged 方法

```ts
// src/api/xxx.ts
export interface XxxListParams {
  tenantId: string
  pageNo: number
  pageSize: number
  // 列出所有后端支持的 filter
  jobCode?: string
  enabled?: boolean
}

export const xxxApi = {
  /** @deprecated 仅限需要全量的特殊场景（如 meta 下拉）。列表页请用 listXxxPaged。 */
  listXxx: ( /* 旧的 fetchAllPageItems 实现 */ ),

  listXxxPaged: async (params: XxxListParams) => {
    const res = await get<PageResponse<...>>('/api/console/queries/xxx', params)
    return {
      records: res.items ?? [],
      total: res.total ?? 0,
      page: res.pageNo ?? params.pageNo,
      pageSize: res.pageSize ?? params.pageSize,
    }
  },
}
```

### 3. Composable 包 TanStack Query

```ts
// src/composables/queries/useXxxPaged.ts
export function useXxxPaged(args: {
  page: Ref<number>
  pageSize: Ref<number>
  jobCode?: Ref<string | undefined>
  enabled?: Ref<boolean | undefined>
  tenantIdOverride?: Ref<string>
}) {
  const tenant = useTenantStore()
  const effectiveTenantId = computed(() => args.tenantIdOverride?.value || tenant.tenantId)

  return useQuery({
    queryKey: computed(() => [
      'xxx-paged',
      effectiveTenantId.value,
      args.page.value,
      args.pageSize.value,
      args.jobCode?.value ?? null,
      args.enabled?.value ?? null,
    ]),
    queryFn: () => xxxApi.listXxxPaged({ /* ... */ }),
    placeholderData: keepPreviousData,
  })
}
```

### 4. View 切换

```ts
// 前
const { data: allData, refetch } = useXxx(tenantRef)
const filtered = computed(() => allData.value?.filter(...)) // 客户端全量过滤
const total = computed(() => filtered.value.length)
const tableRows = computed(() => toPageResult(filtered.value, page.value, pageSize.value).records)

// 后
const serverJobCode = computed(() => filters.jobCode.trim() || undefined)
const serverEnabled = computed(() => filters.enabled ?? undefined)
const { data, refetch } = useXxxPaged({ page, pageSize, jobCode: serverJobCode, enabled: serverEnabled })
const pageRows = computed(() => data.value?.records ?? [])
// 次要 filter（后端未支持的）做本页过滤
const filtered = computed(() => pageRows.value.filter(row => ...))
const total = computed(() => data.value?.total ?? 0)
const tableRows = computed(() => filtered.value)
```

### 5. 搜索 / 重置按钮改成服务端驱动

- `onSearch`：把 `filters.xxx` 反映到 computed params，`page.value = 1`（会自动触发 TanStack Query 重取）
- `onReset`：清 filters + `page.value = 1`
- `@refresh` / `@change`（翻页）：都会自然触发重取，无需手动 refetch

## 注意点

### A. 次要 filter 仅作用于当前页

如果后端不支持某些 filter（例如 `jobName` / `workerGroup` 模糊搜索），**务必**在页面顶部加提示："完整搜索请使用 [支持后端过滤的字段]"。否则用户会困惑"为什么搜不到明明存在的行"。

**长期方案**：推动后端补这些 filter 参数到 `queryXxx` endpoint（见"后端待办"）。

### B. 跨页操作（批量选择）需要额外考虑

如果列表支持多选并批量操作（批准 / 批量启停），"全选当前页"和"全选所有"要明确区分。现有批量审批（`ApprovalList`）使用 `fetchAllPageItems` 聚合后批量提交，迁移时要保留"批量操作时另走一次全量获取"的能力。

### C. `resolveJobDefinitionId` 类的单条查询

这类按 code 反查 id 的场景，本来就应该走 paged `pageSize=1`，不需要 fetchAllPageItems。顺手优化。

### D. TanStack Query `keepPreviousData` 翻页体验

翻页时保留上一页数据直到新数据返回，避免表格"闪白"。上面 composable 模板已带。

- Network 面板看到只拉了 20 条（不是 20000）
