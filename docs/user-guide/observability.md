# 可观测性与排障

> **关注角色**：运维值班、`ROLE_AUDITOR`、`ROLE_TENANT_ADMIN`、`ROLE_ADMIN`
> **操作级别**：查询为低风险；告警确认、投递重试和诊断操作需审慎
> **典型入口**：运行监控、告警与投递、系统管理 → 审计

## 推荐排障路径

1. 从运行总览或告警确认影响范围和开始时间。
2. 获取租户、对象编码、实例 ID 和 Trace ID。
3. 在 Trace 查询中查看关联请求与步骤。
4. 打开作业或工作流运行详情确认失败节点。
5. 若涉及事件投递，检查 Outbox 和通知投递记录。
6. 若涉及配置变化，检查配置变更和操作审计。
7. 只有在根因解除且业务幂等性明确后才重试。

## 告警

告警页按未处理、已确认等状态组织，并支持严重度、类型、时间和 Trace ID 筛选。

- **确认告警**只表示有人接手，不等于故障已恢复。
- **自动归档**或状态恢复不代表受影响业务已经补偿。
- 同一根因可能产生多条告警，先按 Trace ID、对象和时间聚合判断。
- 告警路由规则由有权限的管理员维护，修改后应验证目标渠道和抑制策略。

## Outbox 与通知投递

Outbox 展示待投递、成功、失败或死信等事件状态，用于判断业务事务已提交后，事件是否成功发送到外部系统。

1. 按状态和时间筛选失败记录。
2. 查看事件类型、聚合标识、重试次数和最后错误。
3. 确认下游已经恢复且重复投递可接受。
4. 执行授权的重试或补偿操作。
5. 刷新并确认状态变化；必要时到下游系统核实消费结果。

不要把 Outbox 失败简单归因于前端。前端展示后端状态，实际投递、重试和去重由后端负责。

## Trace ID

Trace ID 是跨页面和跨服务关联一次请求或业务链路的首选标识。

- 从错误提示、实例详情、告警或 Outbox 复制完整 Trace ID。
- 使用专用输入框规范化空格和大小写，不手工截断。
- Trace ID 查不到时核对时间范围、租户、环境和遥测采样策略。
- 对外反馈时可提供 Trace ID，但仍需避免附带凭据、请求正文或个人敏感数据。

## 审计

审计页面回答“谁、在何时、对哪个租户和对象、执行了什么操作、结果如何”。

审计核查建议同时使用：

- 操作者与角色；
- 租户和对象标识；
- 操作类型与结果；
- 请求时间与 Trace ID；
- 变更前后摘要或关联版本。

前端筛选结果是查询视图，不替代后端审计留存。导出或截图应遵循组织的数据处理要求。

## 平台诊断

平台诊断、取证、缓存清理等入口通常只对 `ROLE_ADMIN` 开放。这类操作可能跨租户或影响平台状态，应在明确事故处置流程、影响范围和回滚方案后使用。租户级问题优先通过运行、Trace、Outbox 和审计定位，不升级为平台级写操作。
