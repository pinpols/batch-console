## 高优先级

### 1. 租户上下文存在“静默回退”与“跨账号残留”风险

位置：

- `src/stores/tenant.ts:7-15`
- `src/api/interceptors.ts:11-13`
- `src/api/interceptors.ts:97-100`
- `src/stores/auth.ts:41-49`
- `src/stores/auth.ts:52-59`
- `src/stores/auth.ts:65-70`

问题：

- `tenantId` 默认回退到 `default-tenant`
- 所有请求都会自动带上 `X-Tenant-Id`
- `logout()` 只清 `token`，不清当前租户
- `login()` / `fetchMe()` 只有服务端返回 `tenantId` 时才覆盖本地值

影响：

- 用户登出再登录其他账号时，旧租户可能继续残留
- 系统管理员账号若没有明确回填租户，也会携带旧租户头
- 这类问题不会立即报错，而是把读写操作悄悄落到错误租户，属于高风险数据隔离缺陷

建议：

- 租户上下文不要默认回退到 `default-tenant`
- `logout()` 必须重置租户
- 登录后如果服务端未返回租户，应进入显式选择态，而不是沿用旧值

### 2. 多个列表页通过“拉全量数据 + 前端分页”实现，性能和正确性都有隐患

位置：

- `src/api/adapters.ts:20-64`
- `src/views/system/ConfigManagement.vue:239-266`
- `src/views/system/NotificationManagement.vue:364-368`
- `src/views/system/NotificationManagement.vue:453-457`
- `src/views/system/NotificationManagement.vue:522-547`
- 以及仓库中大量 `toPageResult(...)` / `fetchAllPageItems(...)` 调用

问题：

- `fetchAllPageItems()` 会把接口分页“拉满”后再做前端分页
- 默认上限是 `pageSize=200`、`maxPages=20`，也就是最多只取 `4000` 条
- 超过上限时不会报错，只会静默截断
- 首屏进入时就要把整份列表全部拉下来，筛选/切页也只能靠前端内存

影响：

- 大租户数据下首页加载慢、内存占用高、筛选卡顿
- 用户看到的“总数”和实际后端数据可能不一致
- 对审计日志、变更日志、通知投递日志这类天然会增长的数据尤其危险

建议：

- 改成服务端分页、服务端筛选
- 前端只保留当前页和当前筛选条件
- 如果必须拉全量，至少在 UI 上明确“仅加载前 N 页”的限制

### 3. 配置导入属于高危操作，但当前没有二次确认与强约束

位置：

- `src/views/system/ConfigManagement.vue:319-349`

问题：

- 只要 JSON 能解析成功，就允许直接调用 `importConfigSync`
- `doImport()` 没有要求先预览成功
- 没有二次确认、没有变更摘要确认、没有目标租户提示、没有风险文案

影响：

- 运维人员容易把错误 JSON 或错误租户的配置直接导入
- 这是明显的“高破坏性操作保护不足”

建议：

- 强制“先预览，再导入”
- 导入前弹二次确认，明确租户、变更数量、可能覆盖范围
- 导入按钮应在预览成功前禁用

## 中优先级

### 4. `Ctrl/Cmd + K` 会在输入框场景误触发命令面板

位置：

- `src/layout/DefaultLayout.vue:51-57`

问题：

- 当前只排除了 `contentEditable`
- 没有排除 `input`、`textarea`、`select` 和 Element Plus 输入组件内部节点

影响：

- 用户在表单、筛选框、文本域内输入时，快捷键可能被全局命令面板劫持
- 对重度录入页面是明显的交互打断

建议：

- 对 `INPUT`、`TEXTAREA`、`SELECT`、带 `role="textbox"` 的节点做白名单排除

### 5. 全局滚动条被刻意隐藏，长页面与长菜单的可发现性较差

位置：

- `src/layout/DefaultLayout.vue:214-230`
- `src/layout/LayoutSidebar.vue:138-148`

问题：

- 主滚动区和侧边栏滚动条都被隐藏
- 视觉上更“干净”，但会让用户不容易感知内容可继续滚动

影响：

- 长菜单、长表单、长表格在桌面端的可发现性下降
- 对键鼠混合用户和低熟悉度用户不友好

建议：

- 不要全局隐藏滚动条
- 若要弱化视觉噪音，可改成窄滚动条或 hover 时增强

### 6. 通知与 Webhook 配置表单校验过弱，容易保存无效配置

位置：

- `src/views/system/NotificationManagement.vue:396-418`
- `src/views/system/NotificationManagement.vue:483-500`
- `src/views/system/NotificationManagement.vue:571-587`

问题：

- 渠道仅校验编码和名称非空，未校验 `channelType`、`config` JSON 结构
- 规则未校验 `eventTypes` 是否为空、`channelId` 是否有效
- Webhook 未校验 URL、事件类型、重复值、空白值

影响：

- 前端允许保存明显无效的数据，错误会后移到投递时才暴露
- 用户会感觉“保存成功但功能不可用”

建议：

- 用 `el-form` 规则做前置校验
- URL、JSON、事件列表、渠道引用都要在前端先挡住

### 7. 当前视觉交互偏“炫技”，不够稳重，且在高频操作场景会产生疲劳

位置：

- `src/layout/DefaultLayout.vue:181-203`
- `src/layout/LayoutSidebar.vue:77-84`
- `src/layout/LayoutSidebar.vue:184-249`

问题：

- 主内容卡片、侧边栏、二级菜单都叠加了 hover 位移、scale、描边、阴影
- 交互反馈过多，且作用在布局级容器上，不只是作用在可点击元素上

影响：

- 企业控制台场景下会显得“浮”和不稳定
- 鼠标扫过页面时整体界面持续轻微跳动，长期使用易疲劳

建议：

- 布局级容器取消 hover scale
- 把动效收敛到按钮、菜单项、可点击卡片
- 整体风格更偏稳态、低干扰

### 8. E2E 高度依赖本地固定环境，测试脆弱且容易污染数据

位置：

- `e2e/global-setup.js:6`
- `e2e/global-setup.js:111-152`
- `playwright.config.ts:13-46`

问题：

- 强依赖 `http://localhost:18080`
- 写死 `admin/admin123`
- 启动时会向 `ta/tb/tc` 三个租户导入 Excel 配置包
- 默认租户直接写入本地存储

影响：

- 新同学、本地新环境、CI、共享测试环境都很容易跑不通
- 测试不是只读的，会修改后端状态，重复执行成本高

建议：

- API 地址、账号、种子数据都改成环境变量
- 区分“只读 smoke”和“会写数据的 e2e seed”
- 为测试租户生成隔离命名空间或清理机制

## 低优先级 / 持续优化项

### 9. 构建包体偏大，首屏冷启动成本高

事实：

- `vite build` 输出中存在大 chunk 告警
- `vendor-element-plus` 约 `932 KB`
- `vendor-x6` 约 `548 KB`
- `vendor-echarts` 约 `538 KB`

位置：

- `vite.config.ts:44-55`

问题：

- 虽然做了手动分包，但大依赖仍然集中在少数超大 chunk 里
- 重资源页面并没有继续细化到路由级或功能级延迟加载

建议：

- 对工作流设计器、图表页、复杂后台页做更细粒度的懒加载
- 审视 Element Plus 的按需引入是否还能继续收紧

### 10. 当前单测通过，但测试覆盖面明显偏基础设施，UI 层缺少保护

位置：

- `vite.config.ts:18-25`

问题：

- `vitest` 使用 `node` 环境
- `coverage.include` 只覆盖 `src/api/**` 与 `src/utils/**`
- 页面组件、路由守卫、表单提交流程、权限 UI 基本没有组件级自动化保护

影响：

- 现有单测更像“工具函数回归测试”
- 真正容易回归的 UI 逻辑仍主要依赖人工回归和 E2E

建议：

- 增补关键页面的组件测试或交互测试
- 至少覆盖登录、租户切换、危险操作确认、列表筛选分页、表单校验

1. 租户上下文的默认值与登出清理

3. 把关键日志/管理页改成服务端分页
4. 修复 `Ctrl/Cmd + K` 误触发
5. 收敛通知/Webhook 表单校验
6. 调整布局级 hover 动效与滚动条策略
