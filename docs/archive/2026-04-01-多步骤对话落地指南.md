# AI 协作执行指南

**状态**:Archived
**首次建立**:2026-04-01
**最近修订**:2026-05-14
**适用范围**:使用 AI 助手参与 `batch-console` 前端开发、审查、联调和文档维护时的沟通与交付规范。

本文档由早期“多步骤对话落地指南”整理而来。原文用于把项目从骨架推进到首版可交付状态；当前项目已进入完整业务控制台阶段，因此不再按“第 N 步”驱动开发，改为按任务目标、代码事实和验证结果驱动。

## 1. 协作原则

AI 协作应服务于工程交付，而不是替代工程判断。每次任务都必须先明确边界、确认权威来源，再进入实现或审查。

| 原则             | 要求                                                                           |
| ---------------- | ------------------------------------------------------------------------------ |
| 事实优先         | 以当前代码、后端 OpenAPI、AGENTS.md 和已运行验证为准，不沿用过期报告中的旧描述 |
| 小步闭环         | 每轮只处理一个明确目标；改动应包含实现、验证和必要说明                         |
| 契约先行         | 涉及接口字段、路径或枚举时，先查后端契约，再改前端生成类型和调用层             |
| 用户改动不可覆盖 | 工作区可能有未提交改动；只编辑任务相关文件，不回滚无关变更                     |
| 文档不复制事实   | 长期规范只维护一处；阶段报告描述当时状态，不能替代代码事实                     |

## 2. 推荐任务描述格式

为了减少歧义，给 AI 的任务应包含目标、范围、约束和验证方式。

```text
目标: 修复/实现/审查 ______。
范围: 只涉及 ______ 文件或模块。
约束:
- 遵守 AGENTS.md 中的前端规则。
- 接口以 ../file-batch-system/docs/api/console-api.openapi.yaml 为准。
- 不改移动端测试策略，除非新增独立业务逻辑。
验收:
- 运行 ______。
- 说明改了哪些文件、验证结果和残留风险。
```

如果任务还不清楚，应先让 AI 做只读分析，输出问题清单和建议优先级，再决定是否进入代码修改。

## 3. 常见任务模板

### 3.1 新增或改造页面

```text
请新增/改造 ______ 页面。
先按 docs/design/page-naming-convention.md 判断 URL、代码目录和侧边栏分组。
页面结构复用 PageContainer、PageHeader、SectionCard、ProTable。
依赖 tenant.tenantId 的加载使用 useTenantReload；TanStack Query 场景把 tenantId 放进 queryKey。
完成后运行 typecheck 或说明无法运行的原因。
```

### 3.2 接口联调或类型漂移修复

```text
请对齐 ______ 接口。
先查 ../file-batch-system/docs/api/console-api.openapi.yaml 和后端 Controller/DTO。
如契约变化，先运行 npm run gen:api，再调整 src/api/ 与页面调用。
不要在前端手写与 OpenAPI 分叉的 DTO。
```

### 3.3 UI/UX 审查

```text
请以代码审查方式评估 ______ 页面。
优先列出影响用户路径、信息架构、可访问性、响应式和视觉一致性的问题。
每个问题给出文件位置、证据和建议修复方向。
除非我明确要求，实现改动前只输出审查结论。
```

### 3.4 文档漂移修复

```text
请修复 ______ 文档漂移。
先对照当前代码、README、docs/README 和 AGENTS.md。
只保留当前仍成立的事实；历史结论标注为阶段性或归档。
不要把同一规范复制到多个文档，改为链接权威来源。
```

## 4. 开发执行标准

AI 进入实现前应完成以下判断：

- 本任务是否需要后端契约确认。
- 是否涉及租户上下文、权限、XSS、i18n、移动端路由或 e2e 策略。
- 是否会碰到用户已有未提交改动。
- 是否需要更新文档、测试或生成类型。

实现时遵守以下要求：

- 新页面补齐 `pageMeta.ts`、`locales/zh-CN.ts`、`locales/en-US.ts` 和必要导航项。
- 列表页优先使用 `ProTable + ListPageQueryBar`。
- 状态展示优先使用 `StatusTag` 和后端 meta enum。
- HTML 字符串渲染必须经 `v-safe-html` 或 `purifyHtml()`。
- 页面级操作放在 `PageHeader #actions`；行级操作使用 `RowActions`。

## 5. 验证与交付

交付说明应简洁包含：

- 改动范围：列出核心文件和行为变化。
- 验证结果：列出已运行命令及结果。
- 未验证项：说明原因，例如后端未启动、依赖环境缺失或仅文档改动。
- 残留风险：只写真实存在的风险，不写泛泛而谈的免责声明。

推荐验证顺序：

```bash
npm run typecheck
npm run test:unit
npm run build
```

涉及关键用户路径时，再补 Playwright e2e 或手工浏览器验证。移动端 `/m/*` 仍按根 `AGENTS.md` 的测试策略处理。

## 6. 文档维护口径

文档按用途分层：

- `README.md`：当前工程入口和运行方式。
- `docs/README.md`：文档索引和维护规则。
- `docs/design/`：长期有效的设计和工程规范。
- `docs/reports/`：阶段性分析和当时结论。
- `docs/archive/`：历史流程或已失效材料。

当文档与代码冲突时，处理顺序为：

1. 读取当前代码和后端契约确认事实。
2. 判断冲突文档属于长期规范、阶段报告还是归档材料。
3. 长期规范应修正；阶段报告只追加“当前状态”说明；归档材料只标注适用性，不继续扩写旧计划。

## 7. 不再使用的旧口径

以下早期表述已经过时，不应继续作为任务输入：

- “按第 N 步继续实现页面骨架”。
- “以前端 docs/api 下的 OpenAPI 副本为准”。
- “views 先以页面骨架为主，后续替换业务页面”。
- “前端完全不维护 navigationGroups”。

当前正确口径是：以后端仓库 OpenAPI 为接口权威源；前端保留 `navigationGroups` 作为产品文案、图标和排序来源，后端菜单只控制可见性。
