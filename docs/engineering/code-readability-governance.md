# 前端代码可读性治理

本文是 Vue / TypeScript 可读性改造与评审的工程约束。通用审查流程仍以
[`frontend-quality-review`](../../.agents/skills/frontend-quality-review/SKILL.md) 为准；后端 Java 调用现场遵循配对仓库
[`docs/coding-conventions.md` §1](../../../file-batch-system/docs/coding-conventions.md#1-方法参数约束)。

## 1. 治理目标

- 让调用现场能直接说明“传入什么业务值、为什么这样计算”，而不是让读者反复配对括号。
- 用类型表达合法状态，减少由一组可选字段、多个 `null` 或布尔开关隐式编码的模式。
- 将字符串和派生规则集中到单一事实来源，避免相同 key、路径或协议值在多个组件重复拼装。
- 只把稳定、低误报的机械规则放入阻断门禁；抽象是否适度、局部变量是否有语义由评审判断。

## 2. 方法调用与括号层级

方法实参、`return`、computed 或回调中嵌套了多次转换/调用，并遮住业务含义时，先用有业务含义的局部变量承接，再调用目标方法：

```ts
// 推荐：输入来源和决策步骤可以分别调试
const visibleItems = group.children.filter((item) => !item.hidden)
const visibleCount = visibleItems.length
return total + visibleCount

// 不推荐：多个业务步骤压进一个实参或返回表达式
return total + group.children.filter((item) => !item.hidden).length
```

判断依据是阅读成本，不是固定括号数量：

- 简单的 `t(key)`、`Boolean(value)`、短小的数组映射和单一安全包装保持 inline。
- 多个参数各自包含转换、回退或副作用时分别命名；不要只为拆括号制造 `value`、`data`、`result`。
- fluent 链按语义阶段换行；链中出现分支、远程调用或复用结果时提取命名步骤。
- 提取前后保持求值顺序、调用次数、短路行为、异常时机和副作用不变。
- 只有形成复用的领域操作或独立职责时才抽方法/composable；单次表达式优先局部变量，避免无价值转调层。

自动门禁 `npm run check:readability-calls` 只检查当前分支新增/修改的生产表达式：方法实参或 `return` 内出现至少 3 层连续方法/构造调用时阻断，并提示提取有业务含义的局部变量。短 fluent 链、回调函数体、测试与生成 API 类型不扫描。门禁不推断变量命名质量；普通的两层嵌套仍由评审按本节判断。

## 3. 参数与合法状态

- 方法出现一组共同变化的参数时，优先使用已有的 request/options/context 类型；不要用连续 `null` 或多个布尔值选择模式。
- 互斥节点、请求状态和结果形态使用判别联合，以 `kind` / `status` 等判别字段收窄；不要用一个“全部字段可选”的接口承载多种状态。
- 必填字段在类型或构造边界即为必填；默认值在唯一边界补齐，调用方不重复猜测。
- 参数对象必须内聚，不能演变为跨场景万能对象；只有真实动态 metadata 才使用开放字典。

## 4. 字符串与派生规则

- 用户可见文案只使用 i18n key；同一路径标题通过 `pageTitleKey()` 或 `navigationItemTitleKey()` 生成，不在组件内重复模板字符串。
- 协议值、存储键、路由分组和有限状态集中到常量、`as const` 元组或生成契约；只有使用一次且语义局部的短字符串保留就地声明。
- 多行固定文本使用模板字符串并保持自然排版；JSON、查询参数或请求体优先使用对象/序列化器，不手工拼结构。
- 提取常量以“统一事实或解释业务含义”为目的，不把每个字面量机械搬到远离使用点的位置。

## 5. 设计与抽象

- 优先复用现有组件、composable、store、API client 和纯函数；新增模式必须解决已存在的变化点、重复或测试边界。
- 策略、工厂、适配器等模式按实际扩展点使用，不因名称好看增加接口和单实现包装层。
- 页面、composable 和 store 保持单一主要职责；校验、派生、远程副作用和展示编排混在同一长流程时按业务阶段拆分。
- 数据结构按访问语义选择：唯一性/成员判断用 `Set`，按 key 查找用 `Map` 或受约束注册表，稳定展示顺序用只读 tuple/数组；不要用数组反复 `find` 模拟注册表，也不要用开放字典代替有限联合类型。
- 同一对象承载互斥形态时优先判别联合；构造后不应变化的集合使用只读类型或在边界复制，避免调用方意外修改共享状态。

## 6. 门禁与人工审查边界

| 检查点                  | 自动证据                           | 人工/AI 必审                               |
| ----------------------- | ---------------------------------- | ------------------------------------------ |
| 格式、类型、未声明引用  | Prettier、ESLint、`vue-tsc`        | 命名和换行是否真正表达语义                 |
| 文件/方法规模           | `check:maintainability` 的候选阈值 | 职责是否混杂、拆分是否降低理解成本         |
| i18n、API、架构边界     | 对应治理脚本和契约检查             | 派生规则是否重复、前后端语义是否一致       |
| 嵌套调用、链式表达式    | 格式化只能统一外观                 | 是否需要局部变量、是否保持副作用顺序       |
| `null` 组合、可选字段袋 | TypeScript 可发现部分误用          | 状态集合是否应改为判别联合或具名入口       |
| 设计模式                | 无通用阻断规则                     | 抽象是否对应真实变化点，是否出现无价值套壳 |

评审结论区分明确违约、确认缺陷、建议性改进和未验证风险。多括号、多行或长链只是候选信号，不能单独作为违规结论。

## 7. 变更审查清单

- 调用实参或 `return` 是否需要向内追三层以上才能说清来源？能否用业务命名的局部值降低认知负担？
- 同一 getter、转换、过滤或计算是否重复执行？提取后是否改变了调用次数或时机？
- 是否用多个 `null`、布尔值或可选字段隐式选择模式？类型能否只允许合法组合？
- 字符串常量、标题 key、路径或协议值是否已有权威来源？
- 新增 helper/模式是否被两个以上真实场景复用，或确实隔离了边界？若否，局部变量是否更直接？
- 当前 `Array` / `Set` / `Map` / tuple / 判别联合是否匹配查找、去重、顺序和合法状态需求？是否存在重复线性查找或构造后可变泄漏？
- 自动门禁实际覆盖了什么？未覆盖的语义项是否有针对性测试或评审证据？
