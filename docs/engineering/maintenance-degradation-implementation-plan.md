# Console 维护与降级前端实施方案

## 1. 范围

本方案配套后端维护与降级契约，目标是让 Console 在维护窗口和下游服务异常时：

- 给用户明确、可恢复的状态；
- 禁止用户继续提交不可靠的写操作；
- 区分“系统维护”“下游降级”和“真实空数据”；
- 在桌面端和移动端保持一致。

不新增通用编排、工单、服务网格或独立通知平台能力。

## 3. 前端改造顺序

### P0：维护窗口可用性

1. 扩展维护状态模型：`version`、`updatedAt`、`lastSyncedAt`、`syncError`、`isStale`。
2. 收敛 `useMaintenancePolling`：启动拉取、维护期 10 秒、正常期 30 秒、失败保留最近状态。
3. 建立统一 `useWriteAvailability`，覆盖作业、工作流、批量日、运维动作、配置导入和权限管理页面。
4. 拦截维护 503 后立即导航到 `/maintenance`，保留安全的原始路由。
5. 维护恢复后回跳；回跳失败返回安全首页。

### P1：降级可解释性

1. 根据 `X-Degraded-Source` 展示非阻塞 Banner。
2. 空列表 fallback 显示“下游暂不可用，当前结果可能不完整”，不显示为普通空数据。
3. 正常响应、超时、降级、恢复分别维护明确状态。
4. 统一中英文文案、长文本、无 ETA、跨时区 ETA 的展示。
5. 桌面和移动布局使用同一 store 和状态语义。

## 4. 后端契约依赖

后端是契约权威，前端只消费以下字段和响应头：

```text
GET /api/console/system/maintenance
PUT /api/console/admin/system/maintenance
X-Maintenance
X-Maintenance-Version
X-Degraded-Source
Retry-After
```

维护 503 body 至少包含：

```text
maintenance
readOnly
message
etaAt
affectedServices
version
```

后端未提供 `X-Degraded-Source` 前，前端不能把普通 5xx 或空响应推断为降级。

## 5. 测试与验收

### 单元与组件

- maintenance store 更新、版本覆盖和过期状态；
- 轮询成功、失败、恢复；
- 写操作守卫在全冻结/只读/正常三态下的行为；
- 503 解析和即时导航；
- 降级来源合并、TTL、恢复清除。

### E2E

- 管理员开启全冻结，普通用户从业务页操作后进入维护页；
- 管理员切换只读，读页面可用、写按钮禁用、后端仍拦截写请求；
- 关闭维护后页面自动恢复；
- Trigger / Orchestrator 读接口 fallback 时显示来源 Banner；
- 多语言、移动端和长公告布局不溢出。

### 不纳入本方案

- 不测试或实现新的编排模式；
- 不把故障注入做成前端操作台；
- 不增加独立通知、工单、告警管理产品。

## 6. 完成定义

- 所有重点写页面接入统一写保护；
- 维护 503 可以立即进入维护页并安全恢复；
- 降级不会伪装成真实空数据；
- 后端 OpenAPI、前端生成类型、拦截器、Banner、E2E 文案一致；
- 桌面端和移动端均通过验收。
