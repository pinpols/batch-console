# 浏览器支持策略

## 支持范围

- 桌面：最近两个稳定版本的 Chrome、Edge、Firefox，以及当前和前一主要版本 Safari。
- 移动：当前和前一主要版本 iOS Safari；Android 以最近两个稳定版本 Chrome 为基线。
- 不支持 Internet Explorer、内嵌旧 WebView 和关闭必要 JavaScript/Cookie 能力的环境。

常规 CI 使用 Chromium。`staging-gate` 在 Chromium 全量验收后，还会将 `e2e/smoke.spec.ts` 中标记为 `@cross-browser` 的路由冒烟覆盖 Chromium、Firefox、WebKit 和 Pixel 5（移动 Chrome）配置；它不是全量业务套件的多浏览器运行。移动端触控交互仍需真实 iOS/Android 抽检。

新增语法、Web API、PWA 或加密能力时，必须提供 feature detection 或明确降级，不以浏览器 UA 字符串代替能力判断。

## 认证 Cookie 的并发边界

支持 [Web Locks](https://www.w3.org/TR/web-locks/) 的安全上下文中，当前版本通过同源锁协调密码登录、登出和令牌换发请求，等待前一个请求的网络响应结束后再发送下一个请求。HTTPS 和浏览器认可的 localhost 安全上下文可提供该能力；其他不具备 Web Locks 的环境沿用原有请求行为，跨标签页认证响应可能乱序。

排队等待锁的时限使用请求配置的超时时间；未设置时最多等待 30 秒。等待被取消或超时会报错并停止发送该请求，不会强占其他页面持有的锁；取得锁后的网络请求仍使用其原有超时与取消规则。

该协调只覆盖使用当前前端代码且共享同一锁空间的页面。旧版标签页、未参与协调的客户端、OIDC 跨页面跳转及服务端回调、请求超时或页面中断后的迟到响应仍需分别验证；本机制不改变服务端 Cookie 契约，也不作为这些场景已解决的证据。

当前版本的登录和登出会更新不含身份或凭据的共享代次。其他标签收到变更、恢复显示或重新进入页面时先清除旧资料和权限，再向服务端复核当前身份；发送请求前也会检查已观察的代次。旧标签发起的登出确认会绑定确认框打开时的代次。此机制无法覆盖 Cookie 已更新而通知尚未写入的间隙、未参与通知的客户端、OIDC 回调，或在身份切换前开始但切换后才发请求的所有业务异步流程；它不能替代服务端鉴权或主体一致性校验。
