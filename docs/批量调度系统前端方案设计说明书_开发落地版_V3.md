# 批量调度系统前端方案设计说明书（开发落地版 V3.0）

> 适用范围：批量调度 / 文件导入导出 / 工作流编排 / 执行监控 / 运维控制台  
> 目标读者：前端开发、后端开发、架构师、产品经理、测试工程师  
> 推荐技术栈：Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus + Axios + SSE  
> 文档定位：**开发可以直接按本文档开始编码**  
> **后端接口契约（权威）**：后端仓库 `file-batch-system/docs/api/` 下的 `console-api-protocol.md`（人读协议）与 `console-api.openapi.yaml`（OpenAPI）。**Excel 导入/导出样例与 Workbook 约定**见同仓库 **`file-batch-system/docs/excel-templates/`**（`README.md`、`excel-template-gallery.md` 及各 `.xlsx`）。**控制台 HTTP 前缀统一为 `/api/console/`**；本文档 **第 10 章**（接入规范）与 **第 28 章附录**（路径速查）已与该契约对齐，接口变更须协议、OpenAPI、前端三处同步。

- 页面信息架构

- UI 设计规范

# 2. 系统定位与设计目标

## 2.1 系统定位

该前端系统属于：

- 数据驱动型控制台
- 状态驱动型运维平台
- 配置驱动型业务系统

它不是营销官网，也不是简单 CRUD 后台，而是一个长期在线使用的运维与运营平台。

---

## 2.2 目标用户

- 内部运维
- 内部运营
- 平台管理员
- 任务配置人员
- 监控与排障人员

---

## 2.3 核心场景

- **运营概览**：首屏聚合指标（待审批、告警、运行/失败任务、SLA、Worker 分布、Outbox 积压等）
- 文件中心管理（列表查询 + 归档/删除/重派等治理动作）
- Job / Workflow **配置发布**（含配置版本、灰度、回滚、密钥轮换）
- **Excel 配置维护**（file template / file channel / workflow / job definition 的安全子集：`upload → preview → apply → export`）
- **只读报表导出**（config release、审计、调度快照/历史、worker、outbox 等，仅导出、不回写）
- DAG 编排与查看（拓扑查询 + 设计器；与 workflow query / Excel 域对齐）
- Job Instance / Job Step Instance 执行监控与下钻
- Worker 状态治理（drain、强制下线、已认领任务查看）
- 审批流（单条/批量通过、拒绝）
- 告警、审计、Outbox 等运维查询视图
- 日志/执行轨迹：**优先 query + 可控轮询**；**SSE 待后端在协议中明确端点后接入**（见第 16 章）
- 租户上下文：所有请求须携带**显式 `tenantId`**（query/body/网关映射），以前端选中的租户为准并与后端校验一致

---

## 2.4 UI 目标

- 高可读
- 高信息密度
- 强状态表达
- 长时间使用不疲劳
- 轻动效增强，不炫技
- 适合企业级交付

# 3. 总体技术方案

## 3.1 技术栈

| 分类 | 选型 | 职责 |
|------|------|------|
| 核心框架 | Vue 3 | 组件化与响应式 UI |
| 语言 | TypeScript | 类型安全与工程可维护性 |
| 构建工具 | Vite | 开发、构建、环境管理 |
| 路由 | Vue Router | 页面导航、菜单映射、权限守卫 |
| 状态管理 | Pinia | 全局状态、会话状态、字典缓存 |
| UI 组件库 | Element Plus | 表单、表格、弹窗、抽屉、时间线等基础 UI |
| 请求层 | Axios | HTTP 请求、统一拦截与错误处理 |
| 实时能力 | SSE | 实例日志与状态实时刷新 |
| 图表 | ECharts | 趋势图、失败率、耗时分布 |
| DAG 画布 | Vue Flow（一期） / X6（二期） | DAG 可视化与可编辑能力 |
| 代码规范 | ESLint + Prettier + Husky + lint-staged | 质量与提交规范 |

---

## 3.2 技术选型原则

### 选择 Vue 3 + Vite 的原因

- 中后台场景成熟
- 团队上手成本较低
- 和 Element Plus 结合紧密
- 工程结构清晰
- 适合前后端分离控制台

### 选择 Element Plus 的原因

- 表格、表单、弹窗、抽屉能力完整
- 风格适合运维后台
- 与 Vue 3 集成成熟
- 组件覆盖面高，能够降低初期实现成本

### 选择 SSE 的原因

- 执行日志与状态变更是“持续流式更新”
- 比高频轮询更节省资源
- 非聊天式、非双向强交互场景，SSE 更简单稳定

### 选择 Vue Flow 的原因

- 贴合 Vue 技术栈
- 一期就能快速完成 DAG 页面
- 适合自定义节点、拖拽、缩放、小地图、边编辑

# 5. 权限模型设计

## 5.1 后端角色（Spring Security，以协议为准）

`console-api-protocol.md` 约定控制台使用 **JWT Bearer**（`Authorization: Bearer <jwt>`），并保留旧版 `X-Console-Token` 兼容迁移。服务端角色示例：

| 后端角色 | 能力摘要 |
|----------|----------|
| `ROLE_ADMIN` | 可执行**全部写入**类操作（含配置发布、审批动作、任务触发与治理命令等） |
| `ROLE_CONFIG_ADMIN` | **配置与 Worker 相关**运维写入；非全部写入 |
| `ROLE_AUDITOR` | **运维视图只读**（查询类接口） |

**AI 接口**（`POST /api/console/ai/chat`）除角色外还需 **prompt 授权**检查，前端应单独做入口显隐与失败提示。

---

## 5.2 前端展示角色（可选映射）

产品层可继续沿用「Admin / Operator / Viewer」心智，但**须映射到上述后端角色**（映射表由网关/认证服务与 `GET /api/console/auth/me` 返回体约定）。前端规则：

- **不得**仅依赖 JWT 中的角色 claim 做安全决策；**写入能否成功以 401/403 及业务码为准**（协议明确要求）。
- 路由 `meta` 建议同时支持：`roles: ('ROLE_ADMIN' | 'ROLE_CONFIG_ADMIN' | 'ROLE_AUDITOR')[]` 与细粒度 `permissions: string[]`（后者来自 `me` 接口若扩展）。

---

## 5.3 权限控制策略

### 页面级
- 通过 `meta.roles` / `meta.permissions` 控制菜单与路由进入
- 路由守卫中：未登录 → 登录页；`403` → 无权限页或回退首页

### 按钮级
- 使用 `v-permission` 或 `<PermissionButton />`；**与写入接口同源**：无权限则禁用或隐藏，并避免重复提交

### 数据级
- **租户**：每个请求携带显式 `tenantId`（与协议一致）；前端维护「当前租户」状态，切换后刷新列表缓存
- 行级隔离完全由后端基于 `tenantId` 完成；前端不做「假隔离」

# 6. UI 设计规范

---

## 6.1 设计原则

### 克制
不做花哨演示型风格，不追求“炫酷大屏”，优先保证信息可读与操作准确。

### 一致
颜色、间距、圆角、交互反馈必须统一，不允许页面各自定义风格。

### 分层
页面 > 模块 > 区块 > 元素，层级关系必须明确。

### 状态优先
所有执行型页面，都必须突出状态、时间、结果、异常。

## 6.5 文字层级

- 页面标题：20px / 600
- 区块标题：16px / 600
- 正文：14px / 400
- 辅助信息：12px / 400
- 表格内容：13px ~ 14px

---

## 6.6 动效规范

### 原则
- 时间短：150ms ~ 250ms
- 位移小：不超过 8px
- 场景少：只在必要处出现

### 推荐动效
- 页面切换：淡入 + 微上移
- 折叠展开：高度过渡
- 按钮 hover：颜色过渡
- 卡片 hover：轻微阴影变化或上浮 1~2px
- 状态切换：颜色与文本平滑变更
- Skeleton：替代纯 loading 圈

### 禁止
- 持续闪烁
- 大面积粒子背景
- 多区域同时剧烈运动
- 过长动画

# 9. 状态管理设计（Pinia）

## 9.1 Store 划分

| Store | 职责 |
|------|------|
| useAuthStore | 登录态、JWT、`/auth/me` 主体信息 |
| useTenantStore | **当前 tenantId**（与 ops summary、query 参数联动）；切换租户后清空列表缓存 |
| usePermissionStore | 菜单、按钮显隐（角色/权限来自 me 或网关约定） |
| useAppStore | 布局、主题、表格密度、缓存配置 |
| useDictStore | 状态字典、枚举映射缓存 |
| useMonitorStore | 当前实例上下文、轮询/SSE 连接状态 |
| useWorkflowStore | 当前 DAG 编辑上下文 |

---

## 9.2 不建议放入 Store 的内容

- 页面局部表单值
- 一次性弹窗状态
- 单页面短期查询条件
- 纯展示型本地临时状态

这些应留在页面组件或 composables 中。

# 10. API 接入规范（对齐 `console-api-protocol.md` / OpenAPI）

本章为 **实现约束**：与 `file-batch-system/docs/api` 冲突时以该处为准。

## 10.1 基路径与读写分离

- **Base path**：所有控制台接口位于 **`/api/console`** 之下（Vite 代理可写 `^/api` → 网关，由网关转发到 console 服务）。
- **只读查询**：统一使用 **`GET /api/console/query/...`**，返回 JSON 信封 + 类型化列表 DTO。
- **运维命令 / 状态迁移**：使用 **`POST /api/console/...`**（jobs、files、workers、approvals、config、ai 等），请求体为明确 DTO。
- **类型与 Mock**：优先由 `console-api.openapi.yaml` 生成 TS 类型或 Orval；手工封装时保持 `operationId` 与路径一致便于对账。

## 10.2 Axios 分层

```text
api/
 ├── client.ts         # axios 实例：baseURL、timeout、withCredentials 按环境
 ├── interceptors.ts   # 注入 header、解析信封、HTTP 错误与业务码
 ├── auth.ts
 ├── ops.ts
 ├── queries/*.ts      # 与 /query/* 一一对应
 ├── commands/*.ts     # 与 POST 命令域对应
 ├── excel.ts
 └── reports.ts
```

## 10.3 统一请求头（写入必填）

| Header | 说明 |
|--------|------|
| `Authorization` | `Bearer <jwt>`（首选） |
| `Idempotency-Key` | **所有写入 API 必填**；同一业务动作重试须保持不变 |
| `X-Request-Id` / `X-Trace-Id` | 可选；不传则服务端生成并回显在 `meta` |
| `X-Tenant-Id` | 可选；网关/上游注入；**与 query/body 中 tenantId 的映射关系以前端+网关约定为准** |
| `X-Operator-Id` | 本地可缺省；生产建议由网关注入，用于审计 |
| `X-Console-Token` | 旧版兼容，迁移期保留 |

开发环境可封装 `createIdempotencyKey(prefix)`（uuid / 雪花）并在命令层默认注入。

## 10.4 统一响应信封 `CommonResponse<T>`

```json
{
  "code": "SUCCESS",
  "message": "success",
  "data": {},
  "meta": {
    "requestId": "req-20260321T100000Z-ab12cd34",
    "traceId": "1a2b3c4d5e6f7890",
    "timestamp": "2026-03-21T10:00:00Z"
  }
}
```

TypeScript 示意：

```ts
interface CommonResponse<T> {
  code: string
  message: string
  data: T
  meta: {
    requestId: string
    traceId: string
    timestamp: string
  }
}
```

- **成功判断**：以 **`code === 'SUCCESS'`**（或与 OpenAPI 枚举一致）为准，**不要**再用 `0` / `200` 数字码（与旧稿不同）。
- **traceId 展示**：取自 `meta.traceId`（或响应头映射），用于排障与工单。

## 10.5 分页模型

新列表接口统一采用：

```ts
interface PageRequest {
  pageNo: number    // 1-based
  pageSize: number
}

interface PageResponse<T> {
  total: number
  pageNo: number
  pageSize: number
  items: T[]
}
```

前端 ProTable 分页绑定 `pageNo` / `pageSize` / `total` / `items`，避免各页自定义 `page`/`records` 混用。

## 10.6 错误语义与 HTTP 状态

业务失败时仍可能返回 200 + 信封内 `code`（以 OpenAPI 为准）；HTTP 层：

- **401**：登录/会话失效 → 清 token、跳转登录
- **403**：授权失败 → 与 `FORBIDDEN` 等业务码一致处理

协议列出的业务码基线包括：`INVALID_ARGUMENT`、`VALIDATION_ERROR`、`MISSING_IDEMPOTENCY_KEY`、`NOT_FOUND`、`CONFLICT`、`STATE_CONFLICT`、`UNAUTHORIZED`、`FORBIDDEN`、`BUSINESS_ERROR`、`NOT_IMPLEMENTED`、`SYSTEM_ERROR` 等。

## 10.7 文本安全与 XSS

- 所有服务端字符串按**纯文本**渲染；**禁止**默认 `v-html` / `innerHTML` 渲染 API 文案。
- 审计、原因、描述、prompt 等字段可能经服务端规范化；前端仍按文本节点展示。

## 10.8 Excel 配置维护（四步）

可编辑域（file template、file channel、workflow definition/node/edge、job definition 安全子集）必须走：

**`upload → preview → apply → export`**

- `POST .../excel/upload` → 拿 `uploadToken`
- `GET .../excel/preview/{uploadToken}` → 展示行级校验错误（行号、列名、原因）
- `POST .../excel/apply/{uploadToken}` → 提交写入（仍带 `Idempotency-Key`）
- `GET .../excel/export` → 下载可反复编辑的模板工作簿

**只导出报表**：`GET /api/console/reports/excel/*` 仅下载，不接受 upload/preview/apply。

### 10.8.1 官方模板样例（与运行时导出结构一致）

后端在 **`file-batch-system/docs/excel-templates/`** 维护**给人看的样例工作簿**，与「运行时 `GET .../excel/export` 生成的结构」一致：**数据页必须在第一个 sheet**，用户可导出后按样例修改再上传。详见该目录下 **`README.md`** 与 **`excel-template-gallery.md`**（列名、只读字段、多 sheet 分工以样例与解析器为准）。

| 样例文件（仓库内） | 配置域 | 对应 Console API（Excel 四步） | 说明 |
|--------------------|--------|--------------------------------|------|
| `file-template-config-template.xlsx` | File Template Config | `/api/console/config/file-templates/excel/*` | **优先对齐**：列名与导入解析器一致；`id`/审计字段不开放给用户填 |
| `file-channel-config-template.xlsx` | File Channel Config | `/api/console/config/file-channels/excel/*` | `config_json` 等以 JSON 文本列承载 |
| `workflow-maintenance-template.xlsx` | Workflow 定义 / 节点 / 边 | `/api/console/config/workflows/excel/*` | 适合**迁移/批量维护**；`workflow_code + workflow_version` 作人工关联键；日常更推荐设计器 + 发布单 |
| `job-definition-template.xlsx` | Job Definition（白名单字段） | `/api/console/config/job-definitions/excel/*` | 仅开放**安全子集**；`SYSTEM`/`README` 类 sheet 列系统字段说明 |
| `alert-routing-notification-policy-template.xlsx` | 告警路由 / 通知策略 | **待 OpenAPI 明示**（当前 `console-api.openapi.yaml` 以四类 config Excel 为主） | 对齐 observability / Alertmanager 路由约定；**接口落地前**前端可仅提供模板下载与说明页，或占位菜单 |

**统一 Workbook 结构（与协议、样例一致）**：

- **Sheet1**：`DATA` / `DEFINITION` — 主表，冻结首行；必填浅黄、可选浅蓝、只读灰底；枚举列配合 `DICT` 下拉。
- **`README`**：用途、导入顺序、系统字段说明。
- **`DICT`**：枚举与合法取值。
- **`VALIDATION`**：`preview` 阶段行级错误回写（行号、列名、原因），前端向导须能展示或导出该页。

**前端 Excel 维护向导（`ExcelMaintenanceWizard`）须实现**：

1. 按域拉取 **`GET .../excel/export`** 或提供上述**静态样例**作为「空模板」下载（与产品约定二选一或并存）。
2. **`upload`**：multipart 上传第一个 sheet 为主表的 `.xlsx`。
3. **`preview`**：表格或 `VALIDATION` 风格展示错误列表；支持从错误跳转回对应行概念（列定位）。
4. **`apply`**：确认后写入；全程携带 **`Idempotency-Key`**。
5. 文案明确：**不使用宏**；复杂字段以说明页 + JSON 示例列辅助。

## 10.9 二进制下载例外

- **`GET /api/console/files/{fileId}/download`**：响应为 **原始文件字节**（`Content-Disposition: attachment`），**不属于** `CommonResponse` JSON 信封。Axios 需 `responseType: 'blob'`（或走新窗口/直连 URL），审批策略见协议。

## 10.10 命名与封装示例

# 16. 实时能力设计（SSE 与降级策略）

**当前 OpenAPI 路由目录中未列出执行日志 SSE 端点**；在后端将流式接口写入 `console-api-protocol.md` / `console-api.openapi.yaml` 之前，前端应采用：

- **短周期轮询** `GET /api/console/query/instances`、**`.../query/job-step-instances`** 等，或
- 详情页合并展示 **审计 / 步骤实例** 等已有只读数据

SSE 方案仍作为**推荐能力**保留；一旦后端补充端点（如实例日志流），再接入 `EventSource` 并与 JWT/query token 策略对齐。

## 16.1 适用页面（目标态）

- Job Instance 详情页
- Workflow Run 详情页
- 日志页（指定实例时）
- DAG 运行态详情页

---

## 16.2 SSE 封装建议

```ts
interface SseClientOptions {
  url: string
  onMessage: (data: any) => void
  onError?: (err: Event) => void
  onOpen?: () => void
}
```

封装为 composable：

```ts
useEventStream(url, handlers)
```

## 16.3 前端行为规范

- 进入详情页自动建立连接
- 页面卸载自动关闭连接
- 断开时提示“连接中断，正在重试”
- 支持最多 N 次自动重连
- 重连失败后允许手动重试

## 16.4 日志实时展示规范

- 新日志自动追加
- 默认自动滚动到底部，可手动关闭
- 日志级别上色
- 支持搜索关键字
- 支持复制选中日志

# 24. 最终落地结论

这套前端方案的真正核心不是“选了哪些库”，而是以下三点：

## 1. 表格能力平台化
通过 `ProTable` 统一查询、列表、分页、密度、列配置、抽屉详情，避免页面重复实现。

## 2. 状态体系全局统一
通过字典映射和 `StatusTag` 统一所有状态展示，避免状态口径混乱。

## 3. DAG 能力从查看走向编辑
一期快速落地 Vue Flow，二期再视复杂度升级为更强图编辑引擎，避免一开始过度设计。

# 27. 附录：工程实现最小可运行范围（MVP）

- Worker 列表（`GET /query/workers`）
- 告警列表（`GET /query/alerts`）
- **写入命令统一带 `Idempotency-Key`**（至少打通一类：如 `POST /jobs/trigger` 或审批动作）
- StatusTag + ProTable + LogViewer（日志先轮询/query，SSE 待协议）

这样可以最快支撑平台首版上线。
